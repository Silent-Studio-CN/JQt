> 保护发布凭据与内部信息。**不公开于 README 导航**（维护者专用）。

## 1. 冷邮件 / 增长营销识别（2026-09 实际案例）

收到一封典型模板邮件（发件人 Mercystar <mercystar368@gmail.com>，主题：项目增长建议）。
结构拆解：

| 步骤 | 话术 | 识别要点 |
|------|------|---------|
| 恭维+假装认真 | "I came across JQt and took a look..." | 只引用公开信息（stars/描述/README） |
| 制造焦虑 | "3 stars / 0 fork... harder to recognize value" | 用公开指标暗示你不够好 |
| 通用建议 | "README lead with problem + example + quick start" | 放之四海皆准的正确废话（我们的 README 本就有完整示例） |
| 开放钩子 | "Would you like me to share specific ways?" | 要求你回复 = 进入销售/钓鱼漏斗 |

### 判定清单（收到类似邮件逐条自检）

1. 是否只引用公开可得信息（GitHub API/页面人人可查）？ → 是 = 无诚意功课
2. 是否以开放式提问结尾而非具体干货？ → 是 = 钩子
3. 发件人身份可验证吗（真实项目/社区足迹/组织域名）？ → 否 = 警惕
4. 建议是否不需要了解项目就能写出？ → 是 = 模板
5. 是否催促回复/点击链接/给权限/付费？ → 是 = 直接无视

**验证身份的唯一标准**：对方展示**只有认真读过代码才知道的细节**（具体 API 缺陷、可落地的 PR 级建议）。
**最优应对**：不回复、不点击、不下载。回复 = 确认邮箱活跃 + 进入后续骚扰流。

## 2. 红线（无论对方说什么）

| 对方提出 | 应对 |
|---------|------|
| 链接/附件/二维码 | 不点不下 |
| 推广/SEO/README 优化服务 | 不需要 |
| 合作/成为 contributor/帮提 PR | 拒绝（不解释细节） |
| 问路线图/发布流程/技术栈 | 只答看 README/docs |
| 付费/赞助/投资 | 一律拒绝 |

## 3. 发布凭据隔离原则（历史教训）

- `.signing/`（GPG 私钥、SONATYPE token、cli-1 token）**永不上库**——.gitignore 已固化；git 历史重写已清除早期泄露（2026-09）
- 内部基础设施信息（服务器地址、agent token 位置、控制端路径）**不写入公开文档**——docs/BACKUP 类文件不入库
- `chat/`、内部通道工具（cli1/chat_bridge）不入库（曾有误提交 → 已清除并加固 .gitignore）
- 对外联络邮箱与发布账号（GitHub/Central）**不共用密码**；对外回复用隔离邮箱

## 4. 对外沟通指引

- 用项目隔离邮箱对外（如 silent_user@mail.silentstudio.cn 或大厂邮箱服务），不用个人邮箱
- 回复模板化邮件前先过第 1 节判定清单
